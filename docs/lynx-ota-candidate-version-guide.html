新版本不是下载完，就算正式启用。

这份页面把英文术语统一改成中文：“候选版本安全启用机制”。你可以亲手模拟新版本成功、首屏失败、试运行时杀进程和网络失败。

V2
一句话

这是跨端增强设计。当前 iOS SDK 已提供可选的候选版本安全启用模式；Android/Harmony 仍未接入同等状态机。目标是让新版本先作为候选版本试运行，确认健康以后，才升级成新的当前稳定版本。

试运行版本

候选版本正在接受首屏、接口、原生能力和稳定存活检查，尚未正式替换当前版本。

健康事件

健康确认

首屏成功，关键接口和原生能力可用，页面进入稳定状态后发出的确认。

原子切换

正式启用

候选版本健康以后，把它原子地升级成新的当前稳定版本。

清理动作

放弃候选版本

试运行失败或进程异常退出时，删除候选状态，继续使用原来的稳定版本。

恢复规则

状态可恢复

即使 App 被杀或手机重启，磁盘状态也能知道上次进行到哪一步，不会把半成品当正式版本。

03 / 两种方案的真实差别

不是有没有回滚，而是什么时候改当前版本

你现在的 current/previous 已经可用。增强方案只是在它前面多加一道候选试运行。

下载完成后直接成为当前版本

  1. 下载 V2，校验文件。
  2. 当前版本切到 V2，V1 变成上一版本。
  3. 现有 Tab 继续用旧实例，新页面读取 V2。
  4. 如果 V2 首屏失败，再回滚到 V1 或内置版本。

优点：简单、成熟、已经有完整回滚。
代价：坏 V2 会短暂拥有“当前版本”身份。

候选版本先试运行，成功后再启用

  1. 下载 V2，先记录为候选版本。
  2. 当前稳定版本始终还是 V1。
  3. 冷启动或主动刷新时试运行 V2。
  4. 健康确认后，V2 才正式成为当前版本。

优点：试运行失败时 V1 从未失去稳定身份。
当前实现：iOS SDK 提供 opt-in candidate/trial/confirm/discard/recover API；Android/Harmony 仍需同步。

05 / 你到底需不需要

这是增强项，不是说当前方案错误

当前系统已经有原子 current/previous、首屏回滚和内置兜底，是否增加候选机制取决于业务风险。

可以暂时不做

  • OTA 主要用于非核心展示页面。
  • 发布前已经有严格测试与灰度。
  • 首屏失败后回滚可以接受。
  • 希望先控制三端状态机复杂度。

建议增加

  • 首页、登录、订单或支付高度依赖 OTA。
  • 要求坏版本永远不能成为 current。
  • 需要覆盖试运行时杀进程和重启恢复。
  • 愿意先补自动化故障测试再改状态机。

08 / 常见疑问

最容易混淆的几个问题

候选版本和上一版本是一回事吗？

不是。上一版本是以前已经正式使用过的稳定版本；候选版本是刚下载、尚未正式启用的新版本。方向完全相反。

服务端已经做版本控制，还需要候选试运行吗？

服务端版本控制证明“理论上兼容”；候选试运行证明“在这台设备上实际成功”。如果你的业务允许失败后再回滚，可以暂缓候选机制。

候选版本会不会让磁盘翻倍？

更新窗口内会同时存在当前版本和候选版本，这是为了可恢复。正式启用后只保留 current、previous 和必要的 staging，再由垃圾回收删除孤立 Release。

后台下载新版本以后，当前 Tab 会立刻变化吗？

不会。当前可见 Tab 继续使用自己的旧 LynxView 实例。只有冷启动、重新打开，或者用户主动刷新并成功后，才读取新的已提交版本。

“状态可恢复”到底是什么意思？

App 被杀或手机重启后，客户端仍能从磁盘 state 判断 V2 是候选、正在试运行、已经正式启用，还是应该丢弃。iOS 在开启 candidate 模式后已具备这组字段；默认模式和 Android/Harmony 仍是 current/previous 直接激活。

09 / 推荐落地顺序

先建设测试能力，再升级状态机

STEP 01

建立共享故障夹具

让 Android、iOS、Harmony 使用同一批 V1、V2、坏 SHA、坏首屏和中断场景。

STEP 02

分阶段建设首批 12 项

先落 Android/iOS 可直接开写的 7 项，再补故障点、Harmony Local Test 和三端设备驱动。

STEP 03

先在 iOS 启用候选模式，再同步三端

iOS SDK 已有 opt-in candidate/trial/health 状态机；下一阶段把同一契约迁移到 Android/Harmony，并补设备故障驱动。
