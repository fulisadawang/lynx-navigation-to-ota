02 / IDENTITY

发布版本、包内容、脚本 Map，分别关联

身份回答什么从哪里取
env + hostApp + lynxAppId哪个环境、逻辑宿主和业务 App本次 Runtime 与 prepare / lease / snapshot 的冻结上下文
releaseId / releaseSequence当前页面来自哪次发布实际交付本页面的发布快照
sha256页面实际运行了哪份内容已校验 Bundle 或本次读取字节的实际计算
bundlePath哪个页面、哪个加载图 owner本次清单的真实主包路径
frame debugmetadata:key这一帧使用哪个脚本的映射SDK 的逐帧调试身份
buildId / gitCommit资料是哪次构建产生的模板本次归档，不能代替内容 SHA
V1 用 A，V2 用 B，V3 复用 A

错误显示各自真实 Release；V1 与 V3 的 A 复用相同有效 SourceMap。V2 的 B 始终查 B 的资料，不使用“最新版本”替代。

原生在本次加载和交付字节时冻结身份。Provider 分发时不查询可变的 OTA current；hostApp 是 OTA 逻辑宿主，不能用原生包名代替。直连资源可计算实际 SHA，但未知的 App、Release、路径保持 null。

定位数字为什么新增 reported？

SDK 只给两个原始数字、未明确行列或函数/PC 时，原生保留 reportedFirst / reportedSecond。Server 用逐帧 key 找到唯一脚本后才解释数字。主线程先以官方 function_id / (pc_index - 1) 查 bytecode 位置，再查 JS Map；后台按官方列基准传入。源码结果从 1 起算，列按 UTF-16 代码单元表示。

同 View reload 无法证明错误属于哪次 load 时降低关联精度，保留 View 和帧 key，不补造最新 Bundle 身份。内部 SDK JSON 仅用于投影合同字段，不直接暴露给 Provider。

03 / FLOW

资料跟构建走，错误跟实际加载走

构建资料链路

生产配置构建清理前捕获原始 metadata
→
最终字节核对主包、Async、外部 script 实际 SHA / 大小
→
私有上传并登记上传回读，Server 校验并建立索引
→
原有 OTA 发布公开 Bundle 上传与 Release 流程

使用方式

  1. 在 Release 或制品列表找到对应内容，点击 SourceMap。
  2. 按脚本和文件树阅读源码；文件树可过滤、折叠和分页，代码视图只渲染视口附近的行。
  3. 粘贴原始错误栈或完整 Provider 事件，默认自动反解。手选脚本仅用于没有 key 的帧，不覆盖 SDK 自带的 key。
  4. 点击已映射帧跳到实际源码行列；Async 帧携带自己的 SHA、包路径和 owner，避免误读主包资料。

私有资料

归档位于 .lynx-symbols/…，不进入公开 Bundle CDN、客户端下载清单或 App 资源。Admin 通过鉴权 API 查询 fileId，不拿到对象 key、签名链接或凭据。

准确匹配

索引唯一键是 env + hostApp + lynxAppId + bundleSha256。Release 图限定单个实际 owner；同 SHA 多 owner 无法消歧时拒绝猜测，不跨 App 搜索或使用最新资料。

重跑、冲突与性能边界

私有对象按内容与 metadata 摘要命名，上传前后回读校验。相同语义的登记复用；真正 Map / artifact / bytecode 冲突返回 409。数据库唯一约束负责并发登记，不要求修改 OSS 桶的版本控制状态。

Server 对受控桶读取校验大小与 hash，不接受任意 URL；源码路径只作显示标签。反解在 worker_threads 执行，最多 2 个并发，读取与处理共 45 秒预算，单次 worker 15 秒 / 192 MiB。metadata 16 MiB、单源码 2 MiB、原始栈 128 KiB / 100 帧，Release 图最多 64 个记录 / 64 MiB。忙时返回 429；这些约束降低资源争用，尚无生产负载性能证据。

Async 主线程这次补齐了什么？

Tasm 0.0.53 已在同次 args.debugInfo['main-thread'] 产生真实调试表，collector 0.2.1 只识别 root 键导致初版遗漏。模板在 beforeEmit 保存各输出的实际编码结果，按唯一 assetPath 为归档副本补入 lepusNG_debug_info，核对 function_source 与对应主线程 content 相同，记录 customSections / main-thread。仅资料归档补齐，Bundle Buffer、key 和 Map 没有改写。

Server 从该脚本自己的真实 section / bytecode 读取 Runtime 名称，正确匹配 Async 栈内 main-thread 与 Map 中 main-thread.js。没有借其他脚本的表或凭文件名猜测位置。此前 9 映射 / 3 缺失是初版 collector 遗漏结果，已由最新全部成功结果替代。

06 / DELIVERY

正式启用，按依赖顺序交付

  1. Contracts 0.4.0 正式发布。确认 Server/Admin 固定版本与锁文件对应真实正式包。若正式 tarball 不同，重新生成并验证 integrity。
  2. Server 新索引表和 API。生成 Prisma Client，经授权执行 20261009000000_source_maps 迁移，配置私有桶读取身份。
  3. Admin 与模板 CI。部署查看页，模板配置同一私有桶的读写身份及登记 API。TEST CI 只允许精确登记 POST，不能读源码或反解；PROD 沿用管理权限。
  4. 实际运行接入。正式上线验证时再做云端上传、三端真实错误样本，并将 Provider 接入选定的外部监控平台。本轮未自动执行这些外部动作。
需要配置哪些变量？

SOURCE_MAP_OSS_BUCKET、SOURCE_MAP_OSS_REGION、SOURCE_MAP_OSS_ACCESS_KEY_ID、SOURCE_MAP_OSS_ACCESS_KEY_SECRET；STS 场景加 SOURCE_MAP_OSS_SECURITY_TOKEN。模板已有 OTA_API、TEST CI_RELEASE_TOKEN、人工 / PROD OTA_ADMIN_TOKEN 沿用现有环境管理。只配置变量，不把实际值写入代码、日志或报告。

先前临时设计若仍要求全局发布门禁、OSS 版本控制 Disabled、旧 DTO 或其他与本轮不符的处理，以本实施报告及实际冻结合同为准。
